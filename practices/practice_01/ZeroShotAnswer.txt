
 File  practices/practice_01/TRAINING_PR.diff 
Ниже — замечания к PR, отсортированные по важности, с привязкой к файлам/строкам из диффа.
Findings
1. High Невалидированное тело запроса и риск KeyError  
app/api.py:35-38
- payload: dict и обращение payload["diff"] приведут к 500 (KeyError), если клиент не передаст ключ diff или передаст нестроковое значение.  
- Это также ухудшает OpenAPI-схему и валидацию.
Решение: ввести Pydantic-модель для тела запроса, например ReviewRequest(diff: str), и использовать response_model для ответа.
2. High Нет обработки ошибок LLM  
app/api.py:35-38, app/review_service.py:19-22
- Любая ошибка из review_service.review(...)/llm.generate(...) приведет к 500 без понятного сообщения.  
- Нет ограничений на размер входного diff, что может вызвать таймауты/перегрузку LLM.
Решение: обернуть вызов в try/except, маппить исключения в HTTPException с корректными статусами (например, 400/422 для валидации, 502 для ошибок LLM). Добавить лимит размера diff и/или таймаут.
3. Medium Совмещение слоев: сервис возвращает HTTP-форму  
app/review_service.py:19-22
- ReviewService.review возвращает dict[str, str] с ключом "comment", что вшивает форму HTTP-ответа в доменный сервис. Это затрудняет повторное использование и тестирование.
Решение: вернуть из сервиса строку (комментарий), а форму ответа собирать на уровне API.
4. Medium Аннотации dict[str, str] требуют Python ≥ 3.9  
app/review_service.py:19, app/api.py:36
- Если проект запускается на Python 3.8, аннотация dict[str, str] сломается.
Решение: либо гарантировать 3.9+, либо использовать typing.Dict[str, str] или from __future__ import annotations.
5. Medium Отсутствие схемы ответа и документации  
app/api.py:35-38
- Нет response_model, поэтому схема OpenAPI для /api/reviews не документирует структуру ответа. Это усложняет интеграцию клиентов.
Решение: добавить Pydantic-модель ответа (например, ReviewResponse(comment: str)) и response_model=ReviewResponse.
6. Medium Потенциальная блокировка из-за синхронного вызова  
app/api.py:35-38, app/review_service.py:21
- Эндпоинт синхронный; если LLM-клиент выполняет сетевые вызовы, это может блокировать воркеры.
Решение: либо использовать асинхронный клиент/эндпоинт, либо убедиться, что вызов выполняется в пуле потоков с таймаутом. По возможности — сделать async и не блокировать event loop.
7. Low Безопасность и устойчивость: prompt injection и большие payload  
app/review_service.py:20
- diff напрямую включается в промпт. Злоумышленник может внедрить инструкции (prompt injection). Также нет нормализации/ограничения размера.
Решение: экранировать/делимитировать контент diff в промпте (например, обрамлять маркерами), добавлять системные инструкции/контекст, ограничивать длину и отсекать бинарные/невалидные входы.
8. Low Импорт зависит от внешней инициализации  
app/api.py:30
- from app.dependencies import review_service предполагает корректную инициализацию скоупа зависимостей на импорт. Если там нет созданного инстанса/он зависит от окружения, будет ImportError или неправильная конфигурация.
Решение: проверить, что app.dependencies.review_service существует и правильно настраивается при старте приложения (или внедрять зависимость через DI/Depends).
9. Low Стиль/микро  
app/review_service.py:11-12
- Перенос тела Protocol.generate на новую строку — не проблема, но и пользы не дает. Если линтеры настроены строго, это может флапать форматирование.
Рекомендованные правки (кратко)
1. Ввести модели:
- Request: ReviewRequest { diff: str }
- Response: ReviewResponse { comment: str }
- Обновить эндпоинт: @app.post("/api/reviews", response_model=ReviewResponse)
- Менять сигнатуру на def create_review(payload: ReviewRequest)
2. Обработка ошибок:
- try/except вокруг вызова сервиса
- Конвертировать ошибки LLM в HTTPException(status_code=502, detail="...")
- Валидация размера diff, возврат 413/422 при превышении лимита
3. Разделение слоев:
- ReviewService.review(diff: str) -> str возвращает строку, а не dict
- API формирует { "comment": ... }
4. Совместимость по версиям:
- Проверить целевую версию Python и привести аннотации к ней
5. Безопасность/устойчивость:
- Ограничение размера входа
- Делимитирование вставки diff в промпт
- По возможности — аутентификация/квоты/рейткейпы для эндпоинта

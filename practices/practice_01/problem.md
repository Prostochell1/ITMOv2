# Проблема и метрики

## Проблема

- Пользователь:
  - Клиент API (разработчик или CI/CD), отправляющий diff PR.
- Ситуация:
  - Клиент вызывает POST `/api/reviews` для получения авто‑ревью по diff.
- Что происходит сейчас:
  - Эндпоинт ожидает поле `diff` без валидации; при его отсутствии возникает `KeyError` и 500. Ошибки/таймауты LLM не перехватываются; возможны нестабильные ответы при больших диффах.
- Почему это мешает пользователю или бизнесу:
  - Непредсказуемые 5xx в проде или пайплайнах, отсутствие чётких сообщений об ошибках снижает доверие и автоматизацию.
- Что не входит в задачу:
  - Доработка аутентификации/авторизации, интеграция с реальным провайдером LLM, дизайн UI.

## Метрики

Выберите измеримые показатели, относящиеся к проблеме. Не используйте VTG, IRR, WACC, CSAT или другую метрику только ради названия.

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Доля успешных ответов 2xx на POST `/api/reviews` | Интеграционный тест с валидным JSON и без поля `diff`; доля 2xx на валидном запросе и 4xx на невалидном | >= 99% валидных 2xx, 100% невалидных (без `diff`) возвращают 4xx | До и после изменений | Тесты/лог API |
| Среднее время ответа для небольших diff | Замер через тесты с контролируемым diff | Нормализовать и зафиксировать базовый уровень; выявить регрессии | Регулярно в CI | Тесты/метрики сервиса |

## Почему изменение метрики подтвердит решение проблемы

Если при отсутствии поля `diff` возвращается предсказуемый 4xx, а валидные запросы стабильно дают 2xx и приемлемое время, то пользователи и пайплайны получают воспроизводимое поведение без неожиданных 5xx.

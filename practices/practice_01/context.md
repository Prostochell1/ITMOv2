## Context Pack для первого рабочего сценария

### Факты и правила

- POST `/api/reviews` принимает JSON `{ "diff": string }` и возвращает `{ "comment": string }`.
- `ReviewService.review(diff: str) -> dict[str, str]` формирует промпт: `"Review this pull request and find problems:\n{diff}"` и вызывает `LLM.generate`.
- Источники для анализа: TRAINING_PR.diff и правила из CASE.md (SEC-1, API-1, REL-1, OUT-1, SCOPE-1, QA-1, OBS-1) — только те, что влияют на данный PR.

### Формат входа и результата

- Вход (HTTP): JSON тело с обязательным полем `diff: string`.
- Выход (HTTP): JSON `{ "comment": string }`.
- Внутренний вызов: `review_service.review(diff: str)`.

### Ограничения и запрещённые действия

- Нет явной аутентификации/авторизации в эндпоинте (вне задачи).
- Нет валидации схемы запроса; отсутствие `diff` приводит к ошибке времени выполнения (`KeyError`).
- Не реализованы: SEC-1 (редакция секретов), API-1 (413 при >20 000 символов), REL-1 (таймаут 10с с контролируемой ошибкой), OUT-1 (формат `summary/risks/checks`). Это должно быть отражено как риски.
- В рамках задачи запрещено использовать внешние источники и изменять несвязанные файлы.

### Хороший пример

- Запрос: POST `/api/reviews` с телом `{"diff": "diff --git ..."}`. Ответ 200: `{"comment": "<замечания по PR>"}`.
- Комментарий ссылается на строки diff и/или правило из CASE.md (например, SEC-1) и содержит проверяемую процедуру.

### Плохой пример

- Запрос без поля `diff` или с неверным типом, что приведёт к 500 из-за `KeyError`.
- Комментарии без ссылок на строки diff и без воспроизводимой проверки.

### Что пока неизвестно

- Требования к аутентификации/доступу.
- Политика логирования и мониторинга (OBS-1 задаёт только общую рамку).
- Реальные лимиты размера diff, SLAs и таймауты LLM (требуется согласование по API-1/REL-1).
- Требования к локализации и формату ответа в проде (пока OUT-1 — целевой формат).
